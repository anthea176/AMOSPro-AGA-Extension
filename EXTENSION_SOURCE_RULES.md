Gate A native 130 cas PASS ; premier Runtime WinUAE P2.8 FAIL `ERR 12` (ABK en Fast), révision Chip préparée mais nouvelle Gate B non démontrée au checkpoint, Gate C non démontrée. **Ce repère n'est pas un statut permanent : les commits, candidats et essais plus récents doivent toujours être recherchés.** Le chantier M19 Bob multi-images n'est pas automatiquement livré du seul fait d'une candidate de cache AGPC.

## 2. Cible CPU, ABI AMOS et format AP20

### CPU

- **Cible officielle pour tout nouveau développement : MC68020 / 68EC020 au minimum**, et 68030/040/060 ; aucun nouveau repli fonctionnel 68000/68010 imposé.
- **Décision explicite du 15/11/2026 — 68020 EXCLUSIF :** dès M19 P0a, tout **nouveau code natif AGA** cible le MC68020/68EC020 (et CPU supérieurs). Interdit d'ajouter un nouveau cœur 68000/68010, une double implémentation CPU000/CPU020 ou un repli 68000 pour les Bobs. Les chemins chauds de capture/dessin doivent utiliser une implémentation conçue pour le 68020 (par exemple `BFEXTU`/`BFINS` lorsque le gain est pertinent), et refuser proprement les CPU antérieurs avant toute instruction 020.
- **Preuves CPU obligatoires pour ce chantier :** Gate A avec **modèle réellement configuré en MC68020** (`UC_CPU_M68K_M68020` ou émulateur CPU020 vérifié), décodage `CS_MODE_M68K_020`, tests pixel-exacts + échecs/ABI/relocations. Les anciens PASS en MC68000 restent archivés, mais ne valident **jamais** les nouvelles commandes 68020. **Configuration des essais WinUAE selon instruction de l'auteur : 68030 avec JIT activé pour la validation fonctionnelle (Gates B/C) ; 68020 avec JIT désactivé uniquement pour les benchmarks.** Le code reste ciblé MC68020 minimum. Ne jamais imposer 68020/JIT OFF comme condition d'une Gate B ou C. Préserver byte-for-byte la base historique R88 ainsi que R84 `LAST_GOOD`; ne pas réécrire rétroactivement leur code 68000.

- Conserver les résultats 68000 historiques avec leur version. Des **tests négatifs CPU000** peuvent vérifier qu'une ancienne routine optimisée refuse proprement l'appel ; ne pas en déduire une nouvelle cible supportée.
- Toute détection de CPU exécutée avant le code 68020 doit utiliser des instructions sûres sur le CPU qui l'exécute. Ne jamais supposer l'existence d'un garde CPU global non vérifié.

### Verrou de non-régression CPU / provenance — obligatoire avant toute écriture native

- **Par défaut et sans exception implicite : cible de développement `MC68020` / `68EC020` minimum.** Toute proposition, nouvel émetteur de code machine, routine assembleur ou source d'un builder doit déclarer cette cible *avant la première ligne de code*. Aucun développement « 68000/020 » ni repli 68000/68010 de confort ou de compatibilité. La présence d'instructions communes aux familles 68000 et 68020 n'est pas en elle-même un défaut : c'est **la cible minimale annoncée, vérifiée et testée** qui fait foi.
- **Réutiliser la source du builder du jalon et ses émetteurs natifs vérifiés.** `dist/AMOSPro_AGA.Lib` est une preuve binaire, jamais le code source faisant autorité. Désassembler ou reconstruire des mnémoniques à partir de la `.Lib` est autorisé pour **audit uniquement**, jamais comme solution automatique à une demande de développement « vrai source ». Les sorties de `generate_aga_native_source.py` / `generate_aga_multiunit_source.py` sont des reconstructions partielles, non des sources de production maintenables ou prouvées bit-identiques.
- **Marqueur obligatoire dans les nouveaux fichiers natifs ou modifiés :** `# AGA_NATIVE_MIN_CPU: MC68020` (Python) ou `; AGA_NATIVE_MIN_CPU: MC68020` (ASM). Les exports de désassemblage doivent porter `# AGA_NATIVE_PURPOSE: AUDIT_ONLY` ou `; AGA_NATIVE_PURPOSE: AUDIT_ONLY` et ne peuvent pas se déclarer simultanément source de développement. Les anciens fichiers non touchés conservent leur historique ; toute reprise active impose revue et mise en conformité.
- **Gate automatique :** `python -B tools/native_cpu_policy.py --self-test` puis contrôle Git des sources modifiées via `tools/native_cpu_policy.py --base <SHA_AVANT> --head <SHA_APRES>` ; la CI `.github/workflows/aga-native-cpu-policy.yml` exécute ces vérifications. Une cible 68000/68010 explicite, une double cible 68000/020, un émetteur non déclaré ou un désassemblage présenté comme source font échouer ce contrôle. **Le garde est statique et ne prouve pas la sémantique CPU/ABI** : compléter par assemblage MC68020 réel et Gate A ciblée avant intégration, puis Gates B/C selon le jalon.
- **Incident M19 P0a identifié :** `tools/m19_p0a_amos_bank_transaction_emit.py` annonce « native 68000/020 » et n'a **aucune Gate A CPU** ; il est **prototype préexistant non intégré**, pas un patron à copier. Avant import dans un builder actif ou nouvelle API, revoir explicitement sa cible MC68020, ses octets et ses tests CPU/ABI. Ne pas effacer l'historique ni lui attribuer un PASS rétroactif.
- **Stop avant code si cible/provenance ambiguës :** documenter le builder, la base exacte, les fichiers sources et l'architecture visée ; refuser de produire un nouveau fichier natif jusqu'à résolution. Une description utilisateur « source assembleur » ne justifie jamais de choisir par défaut le 68000 ni de remplacer un source d'origine par une décompilation.


### ABI, paramètres, retours

- Respecter l'ABI d'AMOS Professional 365 et la version **réellement installée** de Compiler. Les paramètres transmis via `GetP` et A3 doivent être consommés conformément au contrat : ne pas restaurer A3 après avoir fait avancer le pointeur de paramètres ; conserver A7 et les autres registres selon le patron validé.
- Pour les fonctions entières du contrat historique : **résultat dans D3, D2=0**. Vérifier les sorties par les vrais wrappers publics AP20, pas le seul noyau natif ; un cleanup ou `MOVEM` ne doit pas écraser la valeur de retour.
- Ne pas déduire une limite « cinq arguments » depuis `Library_GetParams` : la table de collecte des arguments n'est pas la limite générale des signatures AMOS. Confirmer forme fonction/instruction, ordre, nombre d'arguments et tokens avec les sources AMOS/Compiler et les exemples du dépôt.
- Pour les chaînes du loader, contrôler le format longueur + caractères AMOS, convertir proprement vers une chaîne C NUL-terminée pour DOS et libérer le tampon temporaire.
- En cas d'insertions/suppressions dans les unités natives, revalider **les offsets de données et d'état**, LEA, références PC relatives, BRA/BSR/DBcc, `Rbsr` / `Rjsr`, `GetP`, jump table, alignements HUNK/AP20, portées 16 bits, registres, piles, canaries et pointeurs. Les vérifications doivent porter sur **les octets du candidat final** ; ne pas faire confiance au seul générateur.
- Pour `BRA.W`/`BSR.W`, vérifier les bases de déplacement du mot d'extension et les liens inter-entrées. Une table AP20 structurellement valide ne prouve pas que les branchements aboutissent à du code correct.
- L'ancien incident R76 a montré qu'un déplacement de données clavier/souris pouvait provoquer une **écriture dans le code de `Aga Screen Open`**. Auditer les accès à `State+offset` et les LEA dans la version active. Ne pas désactiver les tests négatifs ou les gardes pour obtenir artificiellement un PASS.
- Les définitions NDK des `Screen`, `BitMap`, `RasInfo`, `ScreenBuffer`, `DBufInfo` et offsets AMOS constituent des contrats **à vérifier sur le builder et le code natif de la version cible**. Les anciennes valeurs exactes sont conservées dans l'[archive des règles](docs/EXTENSION_SOURCE_RULES_HISTORIQUE_2026-11-15.md) (notamment anciennes sections 6–7), pas garanties pour toutes les versions. Ne jamais ajouter d'état Bob parallèle non documenté.

### Compiler V1/V2 et tailles

- Maintenir la compatibilité de l'architecture de Compiler effectivement utilisée ; **ne pas imposer les 32 Kio du pont R46 C1 à une architecture V2 en unités**.
- Vérifier **séparément** taille de chaque unité AP20 copiée (le builder R88 contrôle une borne de **65 534 octets**), portées des déplacements relatifs signés 16 bits, liens inter-unités, dispatchers, copies et chargements ; la limite d'une unité n'est pas celle d'un déplacement.
- Protéger les stubs AP20, offsets `GetP`, registres, restauration d'A3 et durée de vie des données. Toute modification du pont nécessite des contrôles natifs de relocation et des essais ciblés ; **une simulation n'est pas une vraie Gate C**.
- Ne pas reconstruire les nouvelles versions systématiquement depuis `LAST_GOOD` ni depuis R46. Relever le **builder, la base binaire figée et le SHA** du candidat actif et n'en dériver une nouvelle version qu'après justification. Conserver les builders R44/R45/R46 et autres sources historiques pour la reproductibilité.
- Le comptage « 50 commandes » et « 57 entrées » appartient à l'historique R46 ; ne l'utiliser jamais pour valider R88 ou une future version. Comparer **l'inventaire exact des tokens, index, signatures et entrées AP20** de la base vérifiée et du nouveau candidat, avec contrôle des commandes héritées, du code public et des chemins internes.

## 3. État partagé, Intuition, écran AGA et Double Buffer

- Avant `Aga Screen Open`, valider le ModeID, la disponibilité du mode via AmigaOS, dimensions, profondeur, overscan, allocations, tags et erreurs `SA_ErrorCode`. Conserver la protection `SA_FullPalette=TRUE` du chemin indexed AGA documenté, sauf correction ciblée prouvée.
- Ne jamais reconfigurer à chaud le ViewPort depuis `Aga Iff Load` via les anciennes séquences `VideoControl/MakeScreen/RethinkDisplay` ayant provoqué un Guru ; préférer une recréation contrôlée d'écran si le besoin a été validé.
- Séquence de test visuel : ouvrir et vérifier le résultat, dessiner et charger en vérifiant les codes, mettre AMOS à l'arrière-plan (`Amos To Back`) pour l'affichage/les touches AGA, puis **`Aga Screen Close` avant `Amos To Front`** sur la sortie normale. Les anciens exemples qui remettent AMOS devant avant fermeture sont historiques, pas des patrons imposés. Tous les chemins d'échec après ouverture ferment/relâchent les ressources acquises.
- En chemin Ctrl+C/Break : traiter correctement les messages IDCMP/RAWKEY, fermer Window, buffers, Screen et restaurer AMOS **avant** d'invoquer le Break natif (`Rjsr L_Test_PaSaut`, après restauration ABI). Un drapeau `BitControl` seul n'est pas une preuve d'interruption effective. Ne pas bricoler le Copper ou modifier `Aga Key` pour contourner un bug natif.
- **Fermeture Intuition :** `CloseWindow` doit précéder `CloseScreen` même lorsque `DBState=NULL`. Vérifier le chemin public de `Aga Screen Close` et le cleanup d'extension, pas seulement un helper isolé.
- **`ChangeScreenBuffer` n'est pas synchrone.** `WaitBlit` seul ne permet pas de détruire `ScreenBuffer` et `MsgPort`. Suivre explicitement les messages `dbi_SafeMessage`/`dbi_DispMessage` en vol, y compris plusieurs swaps, fenêtres d'échec partiel et arrêt Ctrl+C.
- Les réponses Safe/Disp sorties des ports avec `GetMsg` sont **déjà des réponses** : ne pas leur appliquer `ReplyMsg` ; la règle pour les messages IDCMP de la Window est différente.
- **Aucun `WaitPort()`, Exec `Wait()`, retry infini de `ChangeScreenBuffer()` ou attente non bornée** dans une commande exposée à AMOS. Employer `GetMsg` et, si nécessaire, de petits budgets bornés de `WaitTOF`. En cas de dépassement, retourner un échec/pending contrôlé **sans libérer une ressource encore utilisée**. Ne pas effacer artificiellement un état in-flight pour faire paraître le nettoyage terminé.
- Progression des essais : `Open/Close` → allocation DB → un Swap → quelques Swaps → stress et notifications Safe/Disp différées → erreurs/timeout/cleanup/Break → répétition Open/Close en WinUAE. Ne pas commencer un nouveau candidat par un stress test de 100 swaps.
- Toute nouvelle fonction graphique AGA, y compris Bob, dessine dans le **buffer réellement sûr**, respecte la propriété du back buffer et la palette, et ne réalise **aucun `Aga Swap` implicite**, sauf contrat utilisateur spécifique ultérieurement approuvé.

## 4. IFF/ILBM, palettes et banques

- Préserver l'architecture `Inspect → Validate → Decode → Apply` du loader IFF ; ne pas reconstruire un loader monolithique ni toucher à l'implémentation AGAPIC/RLE déjà fonctionnelle pour ajouter des Bobs animés.
- Valider `FORM/ILBM`, `BMHD`, `CMAP`, `CAMG`, dimensions, profondeur, compression, masking, rowBytes, longueur et compatibilité écran **avant écriture palette ou BODY**. Rejeter incompatibilités et débordements proprement sans Guru ni corruption de palette.
- Parcourir les chunks avec taille **big-endian**, padding pair uniquement pour le pas de parcours (`next=data+size+(size&1)`), jamais dans la longueur logique. `rowBytes=((width+15)/16)*2`. BODY : ordre ligne puis plan puis données de ligne. Ne pas convertir silencieusement en chunky.
- ByteRun1 : contrôles 0..127 = copier n+1, 129..255 = répéter 257-n, 128 = NOP. Vérifier les bornes du flux et la largeur des compteurs (ancien défaut `NEG.W` corrigé en `NEG.L` dans le contexte concerné), avec longueur BODY, hauteur, plans et rowBytes.
- `masking=0` était le chemin historiquement qualifié ; un mask-plane ILBM ne peut être revendiqué sans consommation correcte du BODY et tests sur la version cible. Pour les Bobs AGA, **masque 1 bit indépendant** des indices de couleur, selon le contrat distinct en section 5.
- `CMAP` : triplets RGB8, nombre de couleurs à vérifier (`CMAP_size/3`). `SetRGB32` : respecter sa représentation 32 bits et les synchronisations palette/écran qui ont été validées. `CAMG`/ModeID : EHB, HAM, interlace, HiRes et overscan exigent leur propre sémantique ; aucune activation déduite uniquement du nombre de plans.
- Dans une capture vers banque AMOS, contrôler type, numéro déjà occupé, limites géométriques, dimensions nulles/négatives, débordement et overflow **avant allocation**. Un numéro occupé par un format incompatible ou une capture hors limites doit refuser sans écraser une banque existante. Ne pas appeler une routine de réservation destructrice sans validation.
- La transparence par index n'est **jamais implicite** : `-1` = opaque selon les API AGAPIC ayant ce contrat ; `0..(2^Depth-1)` = index explicitement masqué ; vérifier le contrat exact de chaque commande.
- **`Aga Pic Info` est déjà documentée comme API existante**, pas seulement « prévue ». Les deux README décrivent les champs **0..7** : largeur, hauteur, bitplanes, taille CMAP, compression, CAMG original, ModeID d'ouverture, nombre de couleurs écran ; comparer cette table aux octets/tokens de la version installée avant d'en faire un oracle. Les champs 0..5 des premières notes sont historiques.
- **Gestion des banques :** ne jamais supposer qu'une banque numérotée est libre ou qu'un `Load` alloue en Chip. Vérifier type, identité, longueur, remplacement `Erase/Load`, la présence avant `Start(n)`, la durée de vie des références et le format exact `ABK/AmBk`. Les exemples de banque numérotée ne réservent aucune banque secrète.

## 5. M19 — Bobs AGA multi-images (contrat de conception)

**Référence de conception prioritaire :** [`docs/M19_BOBS_MULTI_IMAGE_ABK_API_DESIGN.md`](docs/M19_BOBS_MULTI_IMAGE_ABK_API_DESIGN.md). Les nouvelles commandes et noms **ne sont pas réputés implémentés** par leur présence dans la roadmap. Chaque API publique requiert accord spécifique (paramètres, retours, mémoire, effets, tests), preuve de tokenisation AP20 et Compiler, puis Gates appropriées.

- **Bob logiciel** = dessin Blitter dans les bitplanes de l'écran privé AGA, 1 à 8 plans / 256 couleurs, dimensions variables, plusieurs images dans **une banque ABK AMOS** enregistrable par `Save` et rechargeable par `Load`. Format **planaire non compressé** et masque 1 bit propre à chaque image. **Pas de RLE par frame** ; conserver AGAPIC v1/v2 RLE et Fast pour les grandes illustrations fixes.
- **Indices distincts :** banque AMOS N, image I à partir de 1, objet Bob N indépendant. Une image peut être partagée entre plusieurs objets sans duplication de pixels ; changer de banque active ne rebinde pas les anciens objets.
- **Commandes proposées dans le contrat** : `Aga Bob Bank N`, `Get AGA Bob I,X1,Y1,X2,Y2`, `Make AGA Bob Mask I,C`, `No AGA Bob Mask I`, `Aga Bob N,X,Y,I`, `Aga Bob Bank Free N`. Pour `Get AGA Bob`, **cinq arguments sans `To`, coins inclusifs** : `0,0,31,31` désigne 32×32 pixels. Ne pas lui appliquer les bornes exclusives de `Screen Copy`. Les commandes `Aga Bob Off`, `Aga Bob Update`, `Aga Bob Clear` et `Aga Bob Draw` sont des **cibles P0 encore à valider**, non des instructions présentes par défaut.
- **Gestion mémoire et propriété :** `Aga Bob Bank N` prépare en Chip réelle une représentation DMA exploitable, depuis une banque AMOS éventuellement en Fast ; **aucune autre banque AMOS numérotée** ni `Reserve As Chip Data`/`Bank To Chip`/AMCAF exigée de l'utilisateur. Préparation une fois hors boucle d'animation et une seule représentation Chip partagée entre les objets de la même banque. Vérifier **toutes** les plages source/masque DMA avec `TypeOfMem`/`MEMF_CHIP` ou équivalent OS validé, pas les seuls flags ABK.
- Ne réutiliser directement la banque AMOS en Chip que si **alignement, format, stabilité et durée de vie** sont garantis. Sinon copie privée en Chip. `Aga Bob Bank Free N` invalide les objets dépendants puis libère **uniquement la préparation Chip interne**, sans effacer la banque AMOS sauvegardable, et seulement quand le DMA ne lit plus cette mémoire.
- Après `Erase`, `Load` ou remplacement sous le même numéro, **ne jamais dessiner via un pointeur périmé** ; resélection `Aga Bob Bank N` contractuelle pour re-préparer. Détection des modifications arbitraires in-place via `Poke` non garantie, donc non supportée au contrat initial. Allocation partielle/Chip insuffisante/mauvais format : échec sans demi-état actif ni corruption du buffer.
- Masque indépendant des plans et de la couleur zéro : `No AGA Bob Mask` rend toutes les couleurs opaques, y compris 0 ; `Make AGA Bob Mask I,C` rend transparent l'index C demandé, sans définir la transparence par OR des plans. Tester X impair, 1×1, largeurs 17/31/32/37, bords et clipping pixel exact, profondeur 1/4/8.
- **Blitter R87/R88 :** réutiliser uniquement les éléments compatibles après audit : cache AGPC expérimental **16×16×8** ≠ moteur Bob multi-images à tailles variables ; ne pas importer le wrapper ancien où le masque était dérivé de l'OR des plans.
- Objets persistants, position, image, visibilité, ordre, hotspot et état par buffer ; `Aga Bob Clear/Draw/Update` doivent respecter les deux pages et la restauration de fond. **Aucun Swap automatique** dans ces commandes : un seul `Aga Swap` explicite à l'initiative du programmeur. `Update` vs `Clear+Draw` exige encore un contrat précis, sans supposer la sémantique `Bob Update` native OCS.
- Ordre recommandé après validation individuelle des commandes : P0 banque/capture → masque/Chip → objets → frame complète ; puis P1 lectures/hotspot/priorités/Paste/Limit, P2 collisions/flip/AMAL si approuvés. Le plan n'autorise **ni nouveau code ni création de tests** par lui-même.
- **Sprites matériels AGA** : chantier distinct de Bobs logiciels, canaux DMA/Copper/Intuition et contraintes de palette/largeur propres. Pas de moteur commun ou banque de format interchangeable par défaut. Référence : [`docs/AGA_HARDWARE_SPRITES_S0_S3_ROADMAP.md`](docs/AGA_HARDWARE_SPRITES_S0_S3_ROADMAP.md). Priorité maintenue au socle Bob M19 P0 ; aucun changement sur les Sprites matériels sans audit S0 spécifique.

## 6. Builders, versions et reproductibilité

- Privilégier le **builder reproductible existant** du jalon et ses helpers ; ne pas recréer une chaîne indépendante ou multiplier les builders/ZIP/ASC à chaque petit delta. Une nouvelle version se distingue par son **SHA, sa base, son delta et sa provenance** ; aucun remplacement implicite des anciennes preuves.
- Vérifier sur le candidat exact : structure HUNK/AP20 avec `tools/audit_ap20.py`, tokens et signatures, inventaire des entrées, dispatchers, relocations, taille des unités, CPU requis, contrôles de pointeurs, canaries, absence d'écrasement du code et des ressources conservées. Utiliser les tests CI ciblés du jalon et `tools/build_aga_current.py --verify` selon sa compatibilité **réellement vérifiée**.
- La comparaison avec `LAST_GOOD` ne signifie jamais **égalité obligatoire** entre candidate, `LAST_GOOD` et archives historiques : chaque SHA est indépendant et protégé. Exiger un rebuild reproductible de **la version ciblée** et ne pas substituer un ancien binaire en cas d'échec.
- En cas de FAIL : **conserver les preuves**, rapporter le dernier chemin validé, la cause et la révision ; ne pas restaurer automatiquement `dist/AMOSPro_AGA.Lib` depuis R84 ou un autre état. Toute substitution de ce binaire de travail est une action explicite distincte. Ne pas publier la candidate rejetée comme PASS.
- Identité technique : jalon, version, builder, base, delta, taille, SHA256, commandes et entrées AP20. Le **titre interne** et `$VER:` identifient le binaire ; les statuts `Gate A/B/C/D` et `CANDIDATE/LAST_GOOD` se documentent **hors titre** pour les futures versions. R88 conserve exceptionnellement la chaîne historique `UNINSTALLED GATE A ONLY` : **ne pas modifier ses octets pour une rectification cosmétique**, au risque de rendre invalides les SHA historiques.
- Comparer la table AP20 de la version de référence, et les deux README utilisateur ; ne jamais figer un nombre de commandes/segments issu de R46 dans les vérifications d'une version ultérieure.
- Les outils historiques sous `tools/` restent à leur emplacement et servent aux audits/reproductions. `tools/README.md` doit identifier le builder **actuel** séparément des outils anciens. **Aucun nettoyage ou déplacement automatique** vers `tools/obsolete/` ; ne pas casser les imports ni les chemins CI existants.
- **GitHub CI** : contrôle d'intégrité courant rapide sur la candidate ciblée, et régression historique complète via workflow existant pour un jalon de livraison lorsque pertinent. Ne pas transformer un PASS CI en Gate B, C ou D ni exiger de reproduire toutes les releases historiques après chaque petite correction.

## 7. Protocole de validation et traces

- **Gate A** : audit, préflight ASC, reproductibilité builder, vérification AP20, tests CPU/ABI/canaries/relocations, CI et SHA sur la version exacte. Les émulations Compiler host restent Gate A.
- **Gate B** : exécution **réelle WinUAE/AMOS**, en distinguant explicitement **INTERPRETED** (`Prg State=0`) et **RUNTIME** (`Prg State=1`). Un test Runtime ne vaut pas automatiquement une preuve de mode interprété strict. Enregistrer visuel, comportement, mémoire et fermeture.
- **Gate C** : **nouvel exécutable construit réellement par AMOS Compiler** (`Prg State=-1`), relancé sur la bibliothèque précise. Tester `Aga Screen Open/Close`, pile/registres/relocations et fonctions cibles. Aucun PASS C revendiqué pour le seul layout simulé.
- **Gate D** : essai sur Amiga AGA physique lorsqu'il est disponible/nécessaire ; ne pas transformer un test WinUAE en Gate D.
- **Cadence** : ne pas imposer une compilation manuelle à l'auteur après chaque fonction ou correctif mineur. Regrouper la Gate C réelle aux jalons, avec essai ciblé plus tôt si modification risquée de l'ABI/du pont `Open/Close`. Chaque nouvelle API doit être préalablement approuvée ; aucune Gate n'autorise une promotion automatique.
- **ASC actif** : un seul sous `tests/current/`, syntaxe AMOS Professional vérifiée (blocs `If/End If` sans `Then`), variables/tableaux/labels et banques corrects, boucle bornée, contrôle des erreurs et cleanup. Importer par `Project → Merge ASCII` ; ne pas confondre préflight source avec exécution.
- **Journal texte `RAM:`** pour chaque fin normale PASS ou FAIL, avec ID, version, binaire/SHA si relevable, `RUN_MODE`/`PRG_STATE`, CPU signalé par Exec, `CPU_ATTNFLAGS`, `RESULT`, `VERDICT`, erreurs, mesures Chip/Fast **avant** écriture en RAM:, fermeture et nom du log. `Trap Open Out` et `Trap Close` avec `Errtrap` ; un Guru peut empêcher l'épilogue. Ne pas promettre un PASS si le rapport attendu manque.
- `RAM:` est volatile et `Open Out` écrase les homonymes : **après chaque Gate B/C, sauvegarder les journaux avant reset ou nouvel essai**, ainsi que les captures, derniers repères et informations Guru/ERR. Ne jamais modifier un log a posteriori pour l'aligner sur une version.
- **Benchmarks :** conserver les résultats dans `benchmarks/` sous l'organisation existante, avec test, version et SHA, mode, CPU/JIT/fréquence WinUAE, chipset, résolution/profondeur, banques exactes, médianes et temps par appel. Séparer **draw-only** de **frame complète** (fond, Blitter, VBL, Swap, retries) et préciser si la préparation Chip/décodage est incluse. Aucun FPS ni gain annoncé sans mesure réelle et contrôle de parité pixels.
- **Verdict :** `RESULT 1` ou `CLOSE_RETURNED 1` seul ne suffit pas ; vérifier les critères fonctionnels, erreurs, absence de Guru, état des banques, fermeture et concordance des captures et logs avec le **même ASC exact**. Les Gates restent datées et délimitées à leur scénario.
- **R88 P2.8** au checkpoint documentaire : un premier banc Runtime a renvoyé `ERR 12` avec les banques AGPC en Fast. Le staging dans une vraie banque Chip est seulement une **correction de l'ASC à retester**, pas une Gate B ou C obtenue. Les sources ABK historiques restent dans `tests/fixtures/m19_p28/` ; avant une future campagne, vérifier leurs SHA et **préparer des copies identiques dans `tests/current/` seulement après contrôle et instruction d'exécution**, sans altérer ni déplacer les fixtures de la CI. **Cette consolidation documentaire ne prétend pas les avoir copiées.**
- **Diagnostics :** exploiter les données existantes avant d'ajouter un token, un programme ou un builder. Ne pas reproduire sans besoin les sondes historiques, ni masquer des erreurs natives par un bricolage BASIC. Faire d'abord le plus petit diagnostic discriminant.

## 8. Documentation utilisateur et état du projet

- `README.md` (anglais) et `README.fr.md` (français) sont **deux manuels d'utilisation**, non des journaux chronologiques des Gates. Mise à jour synchronisée lors d'ajout/changement d'une **API effectivement exportée** : nom token exact, forme fonction/instruction, paramètres et unités, retours/sentinelles, mémoire/effets, exemple AMOS vérifiable, version et limites de validation. Les résultats détaillés restent dans `docs/`, `benchmarks/` et les archives historiques.
- Le test `tools/test_readme_api_coverage.py` compare les tokens de `dist/AMOSPro_AGA.Lib` aux deux README : vérifier sa réussite après chaque modification publique de l'API. Ne pas signaler comme livrée une commande uniquement proposée.
- `docs/NEXT_SESSION.md`, `tests/current/README.md` et `docs/ROADMAP.md` suivent la **candidate réelle** et son statut ; `docs/ARCHITECTURE.md` décrit la version et les structures **vérifiées**, en séparant les sections R59/R84 historiques. Les tableaux d'offsets anciens ne prouvent pas leur validité sur R88 ou les versions suivantes.
- `INSTALL.md` et notices d'installation : CPU **68020 minimum**, binaire installable **`dist/AMOSPro_AGA.Lib`**, dépendances réellement requises (`c2p.library` si nécessaire à la fonction), emplacement et environnement WinUAE/Compiler. Ni AMCAF ni une banque particulière ne sont imposées sans preuve pour la nouvelle API Bob.
- Tout ajout de commande nécessite un contrat individuel validé **avant codage**. Une correction interne n'altérant pas l'API approuvée ne requiert pas une nouvelle approbation de signature ; l'ampleur de ses tests dépend du risque. La roadmap ne constitue pas une autorisation d'implémenter.
- En cas de divergence entre un rapport, une ancienne règle et les sources, consigner **ce qui est vérifié, ce qui est supposé et ce qui n'a pas été testé** ; ne pas effacer ni réécrire les preuves.
