# AMOS 365 extension ABI: initial source-backed notes

Reference: https://github.com/marc365/AMOS-Professional-365/blob/master/%2BCompExt.s

Observed in +CompExt.s:
- Header contains offsets to token table, library code, title, and end.
- Token table maps command signatures to library entries.
- `ExtNb equ 5-1` is used to address extension data in the AMOS context.
- Cold start checks `d1` against `"APex"`; on success, installs data/end pointers in `ExtAdr` and returns extension number/version.
- `Lib_Ini`, `Lib_Def`, `Lib_Par`, `Lib_End` are provided by AMOS build macros.

To verify before implementing:
- Reserved/free slot and extension config syntax in AMOS 365.
- Exact numeric-return ABI for a function called by interpreter AND compiler.
- Compiler library embedding/loading rules and extension initialization sequence.
- Chipset detection via graphics.library / chipset registers and CPU checks.
- Correct cleanup and coexistence with AMOS screen/Copper management.

Experimental M0 and M1 AP20 HUNK libraries are now provided, generated by deterministic adaptation of the public-domain Requester binary. Neither is yet assembled from the candidate Genam source. M0 extension dispatch was confirmed working under WinUAE by the developer; M1 compiled/runtime results are pending. In +Music.s and +CEqu.s, integer functions return their result in D3 and call Ret_Int (which sets D2=0).

## M1 runtime finding (31 Oct 2026)

The developer's WinUAE screenshot of the interpreter shows `AGA DETECT = -1`. A follow-up diagnostic confirms its actual numeric value is -1 (adding 1 gives 0). The developer explicitly accepted `-1` as AMOS TRUE. Consequently the public API is boolean: nonzero = detected, zero = not detected. The current machine-code intent was 1, so the exact interpreter/extension return-value transformation remains unproven. Compiled runtime of this particular extension call is not yet confirmed.
